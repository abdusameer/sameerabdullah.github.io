The problem

Many wholesale distributors receive purchase orders as emails and PDF attachments in many different layouts. Someone has to read each one, pick out the customer, SKUs, quantities and prices, check the math, and type it all into the ERP. It's slow, repetitive, and easy to get wrong.

Lumera PO is meant to take on the repetitive part: read the document, extract structured order data, check it with fixed business rules, and hand it to an employee for review. The goal is to work alongside a distributor's existing ERP, not replace it.

How it works

  1. 1Secure sign-inBuilt

    Keycloak handles identity over OpenID Connect with the authorization-code flow and PKCE, encrypted HTTP-only sessions, session expiry, and required MFA. Roles: Organization Administrator, Order Manager, Reviewer, Viewer.

  2. 2Organization isolationBuilt

    Each distributor works in its own organization. Isolation is enforced by application-level authorization and PostgreSQL Row-Level Security, backed by signed tenant contexts.

  3. 3Encrypted PDF uploadBuilt

    Uploads are validated in an isolated, resource-limited process, then stored with AES-256-GCM. The app adds duplicate detection, integrity checks, document history, and recovery from failures.

  4. 4Structured extractionVerifying

    Background workers turn a PO into structured fields: order details, line items, and totals. Today the pipeline runs on a deterministic mock provider so tests are reproducible. Claude API extraction is planned.

  5. 5Deterministic validationIn progress

    Fixed rules check required fields, quantities, prices, line-item math, and totals using exact decimal arithmetic. Problems are flagged for review, never silently corrected.

  6. 6Human reviewPlanned

    Reviewers will compare extracted data against the original PDF and resolve flagged issues. Approval workflows and separation of duties come in a later milestone.

  7. 7ERP integrationPlanned

    Modular connectors, tested first against a simulated ERP adapter, before any live system such as NetSuite, Business Central, or QuickBooks Online.

  8. 8Email intakePlanned

    Verified email intake, and optional tools such as n8n, could submit POs automatically, while authorization and financial decisions stay in the core backend.

Engineering decisions and challenges

AI reads; rules decide

I treat the PDF and the model's output as untrusted input. Extraction proposes values, but deterministic backend validation decides whether the numbers are consistent, and people make the financial calls.

Isolation in the database, not just in queries

Filtering by organization in application code wasn't enough for me. Row-Level Security, signed tenant contexts, and adversarial authorization tests add layers that each have to fail before data leaks across tenants.

Encryption isn't durability

Integrity verification caught missing synthetic test documents during development. That led to a recovery investigation and storage identity checks, so the system now looks for inconsistency instead of assuming that an encrypted file is a safe one.

Testing the tests

A mutation-testing harness deliberately breaks code to see whether the tests notice. An interrupted run once left mutated source behind, so I added a recovery journal, exclusive locking, source-integrity comparisons, and regression tests for the harness itself.
